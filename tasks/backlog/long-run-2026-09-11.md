# Long run on an unfamiliar topic — 6 bugs, 5 fixed

**Setup 2026-09-11.** Fresh deploy `try/plants/`, goal = houseplant care for beginners: a
topic the pack's prompts were NOT written against (they were developed against a nutrition
goal). Backend `http` / `dots-3-note-preview:free`. Brand constraints kept identical to the
nutrition deploy on purpose, so the only variable is the goal and the sources.

**Purpose:** find defects. Every previous live run had produced one, and the rate had not
dropped. It hadn't.

## Result

The pack **generalised** — 6 coherent pages, 0 broken links, 6/6 SEO, 6 licensed images,
content specific enough to act on ("Overwatering kills more houseplants than anything else…
do not water on a calendar schedule"). That was the biggest open unknown and it came out
well.

Six bugs surfaced in five passes. Five are fixed, each with a test written failing first.

| # | bug | found in | status |
|---|---|---|---|
| 1 | phantom tool calls recur on an unfamiliar topic | passes 1-2 | ✅ fixed |
| 2 | tool errors never reach the next run's history | pass 2 | ⚠️ open, DOWNGRADED |
| 3 | capture delivered navigation, not content | pass 3 | ✅ fixed |
| 3b | …the first fix then stopped at the image infobox | pass 5 | ✅ fixed |
| 4 | any 400 permanently disabled structured output | pass 4 | ✅ fixed |
| 5 | stale findings acted on as current state | pass 5 | ✅ fixed |

## 1. Phantom tool calls — the earlier fix was incomplete
`add_asset`, `create_page` and `change_design` called as TOOLS. **13 of 42 calls in two
passes** (31%); `add_asset` alone ten times.

The cost was not wasted steps — it was that **intent was never achieved**: 20 image searches
produced zero images, and the next pass "fixed" the dangling reference by deleting the
`<img>` tag. Self-correction degraded toward the achievable instead of completing the work,
which is what distinguishes this from `website-action-precondition-confusion.md` (closed as a
one-pass tax, correctly).

I had marked the original task's step 4 as unnecessary — *"the generic error proved enough"* —
on the strength of the nutrition deploy. That judgement was wrong; it held only on the topic
the prompt was tuned against.

**Fix:** the unknown-tool error now says where the name belongs, not just what is callable.
Domain-agnostic, so it stays in the core.

**Verified under exercise**, which matters — an absence of phantom calls proves nothing if
the model never tried:

| pass | phantom / total | images |
|---|---|---|
| 1 | 4/14 | 0 |
| 2 | 9/28 | 0 |
| *fix* | | |
| 3 | 0/7 | (no attempt — proves nothing) |
| 4 | **0/21** | **6 downloaded, all licensed** |

## 2. Tool errors never reach history — DOWNGRADED, do not build yet
`Store.recent_failures` reads `outcome` records; a phantom tool call is a `tool_call` span.
So pass 2 repeated pass 1's mistake nine times with no idea it had been made.

**Why it is downgraded:** its only observed symptom was the repetition in §1, and §1's fix
removed that (0 phantom calls in passes 3-6). Feeding every tool error into history would
spend context on a problem that no longer manifests — and `analyze-context-amplification.md`
says that budget is already the binding constraint. Revisit if a *different* repeated tool
error shows up across runs.

## 3 + 3b. Capture delivered furniture, not content
The worst of the set, because it destroyed input silently:

```
article text starts at char 6,140
snippet_max cuts at    char 4,000   → the model received Wikipedia's menu, nothing else
watermark marks the url seen        → that content could never be ingested again
```

Three source pages were consumed and delivered nothing. The model correctly concluded there
was nothing to add — I briefly suspected it of ignoring the metric, which would have been
the wrong diagnosis entirely.

**Fix:** `_strip_nav` drops leading link-only lines and table rows before truncating, and
strips images before deciding whether a line is prose. Conservative by design: **if nothing
looks like prose the page is returned unchanged** — a missed strip costs budget, a wrong
strip costs the content.

**3b:** the first version got past the menu and stopped on the image infobox (218 of 36,848
chars removed). Found only because a later pass still produced no content work.

**Bonus:** the hash is taken over the stripped text, so the fix re-ingested the lost pages
automatically — no watermark surgery.

## 4. A transient 400 permanently disabled structured output
`goal_coverage` died three times with `400 Provider returned error` (upstream `AtlasCloud`).
Reproduced in isolation: no-format, `json_object`, our `json_schema` and a strict-shaped
schema **all succeeded** — so the request was never the problem.

The real defect was ours. `_param_rejected` treated ANY 400 as "this provider cannot take
`response_format`" and set `_schema_ok = False` for the wrapper's whole life. One flaky route
would have silently switched structured output off for every later call in the run. We only
ever saw the loud version (the plain retry hit the same bad upstream); the quiet version
leaves no trace at all.

**Fix:** split the two questions — `_client_refused` (a 4xx I can answer by sending less →
retry plain) from `_param_rejected` (does the error *blame the parameter* → only then
remember it). Both still retry; only the learning is conditional on evidence.
`goal_coverage: 10.0` in the next pass.

## 5. Stale findings acted on as current state
Pass 2's finding, fed verbatim into pass 5:

> "The only remaining issue is a broken image reference in index.html pointing to
> assets/plant-window.jpg, which was never downloaded as a local asset."

Pass 5 restated it in the present tense and edited `index.html` to fix it — while **the same
prompt** carried `broken_links=0` and the asset was on disk, downloaded in pass 4. The loop
re-solved a solved problem and replaced a working image reference doing it.

Purely presentational: findings rendered under a bare `RECENT FINDINGS:` with no age.

**Fix (both packs — the kb pack had the identical line):**
```
FINDINGS FROM PAST RUNS (oldest first). Each describes the site AS IT WAS at that time,
NOT the current state — a problem named here may already be fixed. For what is true
NOW, trust the SITE MAP and the METRIC above.
- 3 runs ago: …
```

This is the most interesting bug of the set: the closed loop's own feedback became the
failure. It and §2 are the same shape from opposite ends — history carrying too little of one
thing and too much of another, with no marking either way.

## Method notes worth keeping
- **Three of my own measurements were wrong before I checked them.** An "exclamation marks"
  constraint violation was `<!DOCTYPE html>`. Pass 3's zero phantom calls proved nothing
  because the model made no image attempts that pass. A "goal_coverage variance" claim rested
  on runs whose log I had since deleted. All three would have gone into a report as findings.
- **Half the bugs were found by inspecting the artifact, not by a run failing.** Every pass
  here exited 0.
